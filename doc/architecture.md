# Photolab アーキテクチャ

RAW 現像ワークフローを支える自作ツール群の設計ドキュメント。
**本ドキュメントが設計上の source of truth** であり、実装より優先される。

---

## 1. 背景と目的

Adobe Lightroom で運用してきた RAW 現像ワークフローを、コスト削減のため
**darktable + 自作の前後工程**で置き換える。

Lightroom は「取り込み・現像・書き出し・配布」を1本で担っていたが、darktable が
カバーするのは現像部分のみである。そこで前工程（取り込み）と後工程（配布）を
自作して補い、Lightroom 相当のワークフロー + α を実現する。

**現像エンジンそのものは自作しない。** darktable はインストール済みのものを使う。

## 3. 中心となる設計原則

### 3.1 darktable は交換可能な部品として扱う

Photolab は darktable の内部状態に依存しない。役割を厳密に分ける。

| 主体 | 持つもの | Photolab から見た扱い |
| :--- | :--- | :--- |
| **darktable** | 現像パラメータ（`library.db` / `data.db`） | **触らない**（読みも書きもしない） |
| **XMP サイドカー** | レーティング・カラーラベル・タグ | **読み取り専用**インターフェース（Phase 3 以降） |
| **Photolab カタログ** | 取り込み記録 | Photolab の専有資産 |

`library.db` を直接読む案は却下した。バージョン間でスキーマが変わる、GUI 起動中は
ロック競合する、darktable の実装詳細に永久に縛られる、の3点による。この分離により
darktable のバージョンアップにも、将来の別ソフトへの乗り換えにも耐える。

**取り込み完了後に darktable を起動する連携は行う**（§5.1 の 6）。
`darktable <取り込み先フォルダ>` とコマンドラインで渡すだけであり、
**内部状態には触らない**ため上の方針に反しない。乗り換え時は起動する
コマンドを差し替えるだけで済む。実行ファイルのパスは `config.toml` に持つ。

#### 対応する現像ソフト（2026-08-12）

`core/developer.py` の `DeveloperSpec` に定義を足せば増やせる。
設定（`config.toml` の `[darktable] developer`）と GUI のコンボボックスで切り替える。

| 現像ソフト | フォルダを開く | JPEG の除外 | 備考 |
| :--- | :--- | :--- | :--- |
| **RapidRAW**（既定） | ❌ | ❌ | [CLI はヘッドレス `export` 専用](https://github.com/CyberTimon/RapidRAW)。フォルダを開く引数が無い |
| darktable | ✅ `darktable <フォルダ>` | ✅ `--conf` | 多重起動不可（`library.db` のロック） |

**RapidRAW は取り込み先フォルダを渡せない。** 起動すると、RapidRAW が設定に持つ
`lastRootPath`（前回開いたフォルダ）が表示される。
設定ファイルを書き換えれば開かせられるが、**他アプリの内部状態に触ることになる**ので
やらない（§3.1 の方針）。起動時に「フォルダは渡していない」旨を利用者に伝える。

> RapidRAW にはペアのグルーピング機能があるため、RAW+JPEG が両方登録される問題は
> darktable ほど深刻にならない可能性がある（未検証）。

#### 現像対象の絞り込み（2026-08-11）

取り込むファイルと現像するファイルは別である。

| フォルダの中身 | 現像したいもの |
| :--- | :--- |
| RAW + JPEG のペア | **RAW のみ** |
| JPEG のみ | **JPEG** |
| 動画 | 現像しない（darktable が対象外） |

darktable 側の設定 `ui_last/import_ignore_nonraws` を `--conf` で一時的に渡して実現する
（`darktablerc` には保存されない）。ただし**この設定はフォルダ単位で JPEG を一律に無視する**。
「ペアのときだけ JPEG を外す」ことは darktable にはできない
（[要望は挙がっているが未実装](https://darktable-devel.narkive.com/hZKNybMG/)）。

そのため Photolab 側で次のように振る舞う。

- **フォルダに RAW があるとき**だけ `ignore_nonraws=TRUE` を渡す
  （RAW が無いフォルダで渡すと何も読み込まれなくなる）
- **RAW が対になっていない JPEG は巻き添えで読み込まれない。**
  該当ファイルを数え上げて利用者に知らせる（`developer.jpeg_only_names()`）
- `JPEG も現像対象にする` のチェックで無効化できる（`config.toml` の
  `[darktable] develop_jpeg`）

**JPEG 単独のカットは GUI のサムネイルに `JPG` バッジ**を出して区別できるようにしている。

### 3.2 写真原本は再取得不可能な資産である

`D:\写真`（約820GB / NEF 18,909枚）はバックアップではなく原本である。
撮り直しができない。**エージェントによる書き込み・削除を機械的に禁止している**
（`tools/hooks/photo_guard.ps1`）。詳細は `agent_execution_rules.md` §1。

### 3.3 カタログは資産管理台帳ではない

Lightroom のような全ファイル管理はしない。カタログが答えるのは
**「このカットは取り込み済みか？」の1問だけ**である。
レーティング・現像状態・書き出し履歴は持たない（Phase 2 で最小限を追加検討）。

## 4. ディレクトリ規約

### 4.1 原画（ローカル）

```
D:\写真\
  ├─ Z6\                      ← 撮影者=本人
  │    ├─ 20260711 ファーストカット\
  │    │    ├─ 20260711-120235_01.NEF
  │    │    ├─ 20260711-120235_01.JPG
  │    │    └─ darktable\      ← darktable の書き出し先
  │    └─ 家\                  ← プロジェクト単位の中間階層（例外的に存在）
  │         └─ 20230711 基礎着工\
  └─ Z50\                     ← 撮影者=妻
       └─ 20251224 クリスマス\
```

- **機種別トップ階層は所有者の区別も兼ねている**ため維持する
- 階層の深さは一定ではない。`家\` のような中間階層、旅行の日別サブ階層が実在する
  → Importer は固定テンプレートで出力先を組み立てず、**親フォルダを選択させる**
- 既存資産の命名は不統一（2021年頃までは `DSC_6642.NEF` のまま）。
  新規取り込み分のみ新規則を適用し、**既存のリネームは行わない**

### 4.2 配布先

```
NAS / OneDrive\写真\
  ├─ 20251224 クリスマス\      ← 機種階層なしのフラット構造
  └─ 20260711 ファーストカット\
```

配布先は機種階層を持たない。Z6 と Z50 の同名フォルダは**1フォルダにマージする**
（原画は機種別に管理したいが、現像後はまとめて見たいため）。

## 5. Importer（Phase 1）

### 5.1 操作フロー

1. **媒体検出** — リムーバブルドライブを列挙し `DCIM/` の有無で候補を提示。
   **ボリュームラベルに機種名が入っている**（実機カードは `NIKON Z 6`）ため、
   これを候補の表示名に使う。出力先の機種フォルダ（`D:\写真\Z6\`）の提案にも使える
2. **メディア選択** — デフォルトは直近に挿入されたもの
3. **サムネイル選択** — グリッド表示。取り込み済みはグレーアウト
4. **出力フォルダ選択** — 親フォルダを選び、その下のフォルダ名を提案しつつ編集可。
   親フォルダは**登録制**（毎回の参照ダイアログを避ける）。
   **日付ごとの振り分け**を任意で選べる（既定オフ / §7）。
   有効時は `<親>\<YYYYMMDD>\`、撮影名を入れると `<親>\<YYYYMMDD 撮影名>\` になる
5. **取り込み** — リネーム + コピー + ハッシュ検証 + カタログ登録
6. **darktable を開く**（任意）— 取り込み先フォルダを引数に darktable を起動する

自動起動は Windows の AutoPlay ではなく**常駐プロセスによるポーリング**で実装する
（AutoPlay は Linux 移管時に捨てることになるため）。Phase 1 では手動起動 +
起動時の自動検出までとする。

### 5.2 命名規則

```
YYYYMMDD-hhmmss_NN.<拡張子>
例: 20260711-120235_01.NEF
```

- `NN` は**秒内連番**（**2桁固定**）。Z6/Z50 は連写で秒10コマを超えるため、
  秒解像度では必ず衝突する（既存資産にも Lightroom が付けた `-2` の痕跡がある）。
  秒間 100 コマを撮れるカメラは存在しないため 2 桁で足りる。
  **99 を超えたら例外を送出して停止する**（黙って上書きしない）
- **採番順序はショットカウント昇順**。取得できない場合は元ファイル名昇順にフォールバックする
- **採番範囲は出力先フォルダの既存ファイルを含む。** 同じ撮影フォルダへ複数回・
  複数カードから追加取り込みする運用が実在するため（§4.1）、既存の使用済み連番は飛ばす。
  走査は**フォルダ直下のみ**で、`darktable\` サブフォルダは見ない（現像後の書き出し先のため）
- 既存資産には旧形式 `YYYYMMDD-hhmmssNNN`（3桁・アンダースコアなし）が実在するが、
  **末尾3桁は秒内連番ではない**（取り込みバッチ単位で一定）。
  アンダースコアの有無で新形式と文字列衝突しないため、連番の消費対象に含めない
- **動画も静止画と同じ規則に揃える**。ただし**撮影日時はファイル更新日時から取る**。
  QuickTime `mvhd` の `creation_time` は使わない（下記）
- RAW + JPEG ペアは同一の basename を共有する（1カットとして扱う）
- **撮影日時が取得できないファイルはリネームしない。** 元ファイル名のまま取り込み、
  GUI で警告する。想定ケースは Nikon 以外の未対応フォーマットが混ざった場合。
  撮影時刻に見える偽の日時をファイル名に焼き付けるより害が小さい。
  このカットは秒内連番を消費しない

実装は `photolab/core/naming.py`。

#### 動画の撮影日時（2026-08-09 に方針変更）

当初は「Nikon の MOV は `mvhd` にローカル時刻を書くので変換不要」としていたが、
**これは古い世代のファイルにしか当てはまらなかった**。既存資産と実機カードの
MOV 21 件を実測した結果:

| 撮影時期 | `mvhd` の中身 | 件数 |
| :--- | :--- | ---: |
| 2019 〜 2021 | ローカル時刻 | 6 |
| **2022-06 以降** | **UTC**（9時間ずれる） | 14 |

同じ Z6 でもファームウェアの更新で規格準拠（UTC）に変わったと思われる。
`mvhd` だけを見ると**現行機の動画が 9 時間ずれた名前になる**。

**採用する方針**: 動画の撮影日時は**ファイル更新日時（mtime）**から取る。
どちらの世代でも mtime は一貫してローカルの撮影時刻だった
（カードの FAT32 にカメラがローカル時刻で書くため）。
Importer はカードから直接読むので mtime は信頼できる。

`mvhd` の値は `metadata.read_mvhd_creation()` で取得でき、整合性の確認に使える。

### 5.3 重複判定キー

カタログの唯一の存在意義であり、本プロジェクトの技術的な肝。

強い順に3段階へ落ちる。2段目以降は GUI で警告する。

| 条件 | 種別 | 形式 |
| :--- | :--- | :--- |
| シリアル + ショットカウントあり | 静止画キー | `nikon:{serial}:{shutter_count}` |
| 撮影日時あり（動画 / MakerNote なし） | 退避キー | `t:{captured_at}:{source_name}:{size}` |
| 撮影日時もなし（未対応フォーマット） | 名前キー | `n:{source_name}:{size}` |

2段目以降が弱いのは、カードをフォーマットするとカメラが `DSC_0001` から
元ファイル名を振り直すためである（別カットを取り込み済みと誤判定しうる）。

Nikon の MakerNote に含まれる **シリアル番号 + ショットカウント** はボディごとに
完全に一意で、リネームやコピーでも壊れない。カードをフォーマットせず使い回しても、
別カードに同じカットが入っていても正しく判定できる。

**取得手段は自前実装**（`photolab/core/metadata.py`、標準ライブラリのみ）。
NEF は素の TIFF であり、Nikon MakerNote は `Nikon\0` + version(2) + padding(2) の
10バイトヘッダの後に**埋め込み TIFF ヘッダ**が続く（MakerNote 内のオフセットは
この埋め込みヘッダが起点）。`0x001d` SerialNumber と `0x00a7` ShutterCount は
**平文**で格納されている。

`pyexiv2` は GPL-3.0 のため製品コードでは使わない（§7）。

**検証結果（2026-08-09）**:

- 既存資産から 200 枚をランダム抽出して **200/200 で取得成功**
- ボディ 2 台がシリアルで明確に分離できる（Z6: 2007594 / Z50: 2021917）
- **NEF と JPG で serial / shutter_count が完全一致** → RAW+JPEG ペアの同カット判定に使える
- `pyexiv2` との突き合わせで**不一致 0 件**（タグ解釈の正しさを確認済み）

**取得できなかった場合は動画と同じ退避キー `t:{captured_at}:{source_name}:{size}` を使う。**
このキーはカードのフォーマットで元ファイル名が振り直されると弱くなるため、
**使用時は GUI に警告を表示する**。

### 5.4 サムネイル表示

NEF の**埋め込み JPEG プレビュー**を取り出す。フルデコード（デモザイク）は行わない。
`rawpy.imread(path).extract_thumb()` は埋め込み JPEG のバイト列を
デコードせずに返すため高速。取り出したプレビューを長辺 512px に縮小し、
ローカルにキャッシュする（1枚あたり約 20〜46 KB / 355 カットで 16 MB 程度）。

**並列化の方針（2026-08-10 の実測で変更）**: 当初は「カード読み出しが律速なので
ワーカースレッドで並列取得」としていたが、実測すると**読み出しの並列化は逆効果**だった。

| 工程 | 直列 | 4並列 | 8並列 |
| :--- | ---: | ---: | ---: |
| I/O（カードからプレビュー取り出し） | 156.5 ms/枚 | \- | \- |
| CPU（縮小・再エンコード） | 84.8 ms/枚 | 22.3 ms/枚 | 15.4 ms/枚 |

I/O はカードの実効速度（約 40 MB/s）で頭打ちであり、並列に読むとシーク競合で
かえって遅くなる。一方 CPU 側は 8 並列で 5.5 倍になる。
**読み出しは直列、縮小だけを並列**にする（`ThumbnailCache.generate_many()`）。
355 カットで約 61 秒の見込み。

> 計測上の注意: スレッド数を変えて同じファイルで測ると OS のページキャッシュに
> 載って無意味な数字が出る。`scan_card()` が全ファイルの先頭 2MB を読むため、
> 走査後は特に汚染されやすい。I/O と CPU を分けて測ること。

**JPEG 単独カットも一級市民として扱う。** 既存資産の実測（2026-08-09）では

既存資産の実測（2026-08-09）では Z50 は JPEG 中心だった。

| 機種 | NEF | JPG | MOV |
| :--- | ---: | ---: | ---: |
| Z6 | 18,777 | 24,114 | 20 |
| Z50 | **132** | **906** | 0 |

RAW 撮影を前提に設計すると Z50（撮影者=妻）の実態と合わない。
サムネイル取得は **NEF の埋め込み JPEG 経路と、JPG をそのまま縮小する経路の両方**を持つ。
`rawpy` だけでは足りず、縮小に `Pillow`（MIT-CMU）を使う。

#### 動画のサムネイル（2026-08-11 に方針変更）

当初は「Phase 1 では作らない」としていたが、**Nikon の MOV は
`moov/udta/NCDT` に JPEG を埋め込んでいる**ことが分かったため対応した。
**動画をデコードしないので ffmpeg 等の依存は不要。**

| アトム | 解像度 | 用途 |
| :--- | :--- | :--- |
| `NCVW` | 1920×1080 | これを使う |
| `NCM1` | 640×360 | `NCVW` が無い場合 |
| `NCTH` | 160×120 | 最後の手段 |

**実測（2026-08-11 / 既存資産と実機カードの MOV 24 件）**: 23 件で取得成功、
1 件のみ失敗（iPhone の `IMG_2828.MOV`。NCDT を持たない）。1 件あたり 30〜60 ms。
`mvhd` と違って**世代差はなく、2019 年のファイルでも取得できた**。

NCDT を持たない動画（他社製カメラ等）はサムネイルなしとし、GUI が代替アイコンを出す。

（Z6 の JPG 数が NEF を上回るのは `darktable\` 配下の書き出し JPG を含むため。
これは取り込み対象ではない）

### 5.5 除外ファイル

実機カード（Nikon Z6 / FAT32 / 2026-08-09 実測）の構造:

```
L:\                              ← ボリュームラベル 'NIKON Z 6'
  ├─ DCIM\102NCZ_6\              ← 取り込み対象はここだけ
  │    ├─ DSC_4590.NEF / .JPG
  │    ├─ DSC_4657.JPG           ← JPEG 単独（実在する）
  │    ├─ DSC_4659.MOV
  │    └─ NC_FLLST.DAT           ← 除外
  ├─ NIKON\Z_6                   ← 除外（カメラの管理ファイル）
  ├─ System Volume Information\  ← 除外
  └─ NIKON001.DSC                ← 除外（カメラの管理ファイル）
```

方針は2段構え。

1. **`DCIM/` 配下だけを走査する。** ルートにはカメラや OS の管理ファイルがある
2. **取り込み対象は許可リストで決める**（`.NEF` `.JPG` `.JPEG` `.MOV` `.MP4`）。
   知らない拡張子は持って行かない

明示的な除外（許可リストでも弾けるが、意図を残すため保持する）:

- `NC_FLLST.DAT` — Nikon がカードに書く管理ファイル（既存資産に76個混入している）
- `.THM` / `.LRV` — 付随ファイル
- ドット始まりの隠しファイル

### 5.6 コピー検証

コピー後にハッシュ照合する（xxHash3）。写真データであり、**サイレントな破損は許容しない**。

実装は `photolab/core/copier.py`。

- **コピーしながらコピー元のハッシュを計算する**（元ファイルを読み直さない）。
  その後コピー先を読み直して照合する。カード読み出しが律速なのでデータに触る回数を抑える
- **コピー先に同名ファイルがあれば上書きせずエラー**にする（`DestinationExistsError`）。
  連番の採番（§5.2）で衝突は避けているが、それが破れた場合の最後の砦
- **照合に失敗したらコピー先を削除する**（`HashMismatchError`）。
  上書きを先に弾いているため、ここで消すのは自分がこの呼び出しで作ったファイルに限られる。
  破損したファイルを正常な名前で残す方が写真の資産としては危険である
- 元ファイルの更新日時を引き継ぐ（撮影時刻の手がかりとして残す）

**実測（2026-08-09 / 実機カード → ローカル SSD）**: 約 44 MB/s。
カード読み出しが律速。355 カット・約 12GB のカード1枚で 5 分程度の見込み。

## 6. Exporter（Phase 2）

`<撮影フォルダ>\darktable\` を監視し、配布先へ再配置する。

- **配布先はプロファイルとして複数定義**し（名前 + パス）、実行時にチェックボックスで選択する。
  共有相手によって OneDrive のみ、バックアップ目的なら NAS のみ、といった使い分けをする
- 配置先は `<配布先ルート>\<撮影フォルダ名>\`（機種階層は落とす）
- 同名フォルダが既にある場合は**マージ**する

現行は手作業でコピーしフォルダ名を直しており、その過程で日付や名前の揺れが
発生している（ローカル `20251215 お宮参り` に対し OneDrive `20251209 お宮参り` など）。
**既存の配布先資産とローカルは機械的に対応が取れないため、Exporter は今後の分のみを扱う。**

## 7. 確定した設計判断（やらないこと）

レビューの蒸し返しと、引き継ぎ先での再提案を防ぐために記録する。

| 論点 | 判断 | 理由 |
| :--- | :--- | :--- |
| darktable の `library.db` を読む | **やらない** | スキーマ変更・ロック競合・実装依存 |
| Photolab から XMP を書く | **やらない**（Phase 1-2） | 現像パラメータの持ち主は darktable ひとつに限る |
| 既存 18,909 枚をカタログに遡及登録 | **やらない** | 目的は取り込み済み判定のみ。必要になれば後から追加可能（§5.3 のキーは既存 NEF にも生きている） |
| 既存ファイルのリネーム | **やらない** | 原本への破壊的操作。命名の不統一は許容する |
| 取り込み時に日付でフォルダ**自動**分割 | **既定ではやらない**（任意機能としては提供する / 2026-08-11 更新） | 1枚のカードに複数日が混在し、1フォルダにまとめる運用が実在する（`20211202 東寺` に 11/28 撮影の MOV）。**自動でやらない**という判断は維持し、明示的なチェックボックスで選べるようにした（§5.1）。Z50 の資産には `20260101` のような日付のみのフォルダも実在するため、需要自体はある |
| Exporter を darktable-cli 方式にする | **やらない**（Phase 2 時点） | 目的が PC 破損時のバックアップであり、再現性の高い再書き出しは現時点で不要。将来 Publish Services 相当が欲しくなったら再検討する |
| 取り込み時に初期 XMP を生成（Apply During Import 相当） | **やらない**（Phase 1-2） | 有用だが XMP history stack の自前生成が必要で難易度が高い。Phase 4 の候補 |
| worktree / サブエージェント委譲 | **使わない** | プロジェクト規模に対して過剰 |
| 製品コードで `pyexiv2` を使う | **やらない** | GPL-3.0（下層の exiv2 も GPL-2.0）。本体は MIT で配布するため汚染源になる。EXIF / MakerNote は自前実装で足りることを実証済み（§5.3）。開発時の答え合わせ用途にのみ `requirements-dev.txt` で使う |
| GUI に PyQt を使う | **やらない** | PyQt5/6 は GPL。PySide6（LGPLv3）を使う |
| 取り込み後にカード上のファイルを削除する | **やらない** | 削除はカメラでのフォーマットに任せる。ツールが原本を消す動線を作らない |
| 取り込み中断時にコピー済みファイルをロールバックする | **やらない** | 出力先の削除処理を持たせない。`import_batch.status = aborted` の記録に留める。中途半端なファイルは次回の重複判定で識別できる |
| Importer の独立した仕様書（`doc/importer_spec.md`）を作る | **やらない**（当面） | source of truth を増やさない。本ドキュメント §5 が仕様の置き場所。§5 が肥大して「全体を掴む」役割を壊し始めたら、そのとき分離して §5 からリンクする |

## 8. 技術スタック

| 用途 | 選定 | 備考 |
| :--- | :--- | :--- |
| 言語 | Python 3.12 | 将来の Linux 移管を考慮 |
| GUI | **PySide6** 6.11 | Qt の公式 Python バインディング（**LGPLv3**）。サムネイルグリッドは `QListView` の IconMode。Linux でそのまま動く |
| サムネイル抽出 | `rawpy` (MIT) | NEF の埋め込み JPEG をデコードせず取得。JPG は別経路（§5.4） |
| サムネイル縮小 | `Pillow` (MIT-CMU) | `draft()` で libjpeg の DCT スケーリングを使い間引いてデコードする。アプリアイコンの生成にも使う（`tools/make_icon.py`） |
| EXIF / MakerNote | **自前実装**（標準ライブラリ） | `core/metadata.py`。GPL 依存を避けるため（§5.3 / §7） |
| ハッシュ | `xxhash` (BSD-2) | xxHash3 |
| カタログ | 標準 `sqlite3` | `%LOCALAPPDATA%\Photolab\catalog.db` |
| テスト | `pytest` | |

> **Qt と PySide6 の関係**: Qt は C++ の GUI フレームワーク本体、
> PySide6 はそれを Python から使うための**公式バインディング**であり、択一の関係ではない。
> 「PySide6 を使う」＝「Python から Qt を使う」。
> 非公式バインディングの PyQt5/6 は GPL のため採用しない（§7）。

**ライセンス方針**: 本体は MIT。**製品コードに GPL の依存を持たない**。
詳細は `NOTICE.md`。開発時のみ `pyexiv2`（GPL-3.0）を自前パーサの検証に使う。

## 9. カタログスキーマ（**確定** / 2026-08-09）

```sql
-- 取り込みバッチ（1回の取り込み操作）
CREATE TABLE import_batch (
    id           INTEGER PRIMARY KEY,
    started_at   TEXT NOT NULL,      -- ISO8601 ローカル時刻
    finished_at  TEXT,
    source_label TEXT,               -- ドライブレター / ボリューム名
    dest_root    TEXT,               -- 出力先フォルダ
    file_count   INTEGER,
    status       TEXT NOT NULL       -- running / done / aborted
);

-- 取り込み済みメディア（重複判定のためだけに存在する）
CREATE TABLE imported_media (
    id              INTEGER PRIMARY KEY,
    dedup_key       TEXT NOT NULL UNIQUE,   -- §5.3
    is_fallback     INTEGER NOT NULL DEFAULT 0,  -- 弱いキー（t: / n:）で登録されたか
    camera_model    TEXT,
    camera_serial   TEXT,
    shutter_count   INTEGER,
    captured_at     TEXT,                   -- ISO8601 ローカル時刻
    source_name     TEXT,                   -- カード上の元ファイル名 (DSC_1234.NEF)
    dest_path       TEXT NOT NULL,
    dest_name       TEXT NOT NULL,
    file_size       INTEGER,
    content_hash    TEXT,                   -- xxh3
    imported_at     TEXT NOT NULL,
    import_batch_id INTEGER NOT NULL REFERENCES import_batch(id)
);

CREATE INDEX idx_media_captured ON imported_media(captured_at);
CREATE INDEX idx_media_batch    ON imported_media(import_batch_id);

-- スキーマのバージョン。Phase 2 での拡張に備える
CREATE TABLE schema_version (
    version INTEGER NOT NULL
);
```

実装は `photolab/core/catalog.py`（`SCHEMA_VERSION = 1`）。設計上のポイント:

- **`dedup_key` の UNIQUE 制約が二重取り込み防止の最終防衛線**である
- 再取り込みは **UPSERT**（`ON CONFLICT(dedup_key) DO UPDATE`）で扱う。
  新規レコードを作らず `dest_path` 等を上書きする。**カタログは履歴を持たない**（§3.3）。
  媒体は取り込み後に消す運用のため、重要なのは「取り込んだか」の一点であり、
  `dest_path` は参考情報として正確な追跡を保証しない
- `is_fallback` は弱いキー（`t:` / `n:`）で登録されたことの記録。GUI の警告表示と、
  後からの棚卸しに使う
- `imported_keys(keys)` で一括問い合わせできる。GUI のサムネイルグリッドが
  1枚ずつ問い合わせずに済むようにするため

### 9.1 カタログの点検（`core/maintenance.py`）

カタログと実ファイルは独立に動く。取り込んだ後に手でファイルを消すと
**カタログだけが「取り込み済み」と言い続け**、そのカットは次回グレーアウトされて
既定で選択されなくなる（誤って取り込んだ分を消したときに実際に起きた）。

- `check_catalog()` が食い違いを検出する（既定は存在確認のみ。
  `verify_hash=True` でハッシュも照合するが全ファイルを読むので遅い）
- `remove_missing()` が実ファイルの無い記録を削除する。
  **写真そのものには触れない。** 記録が消えたカットは「未取り込み」に戻る
- 起動時に `abort_stale_batches()` で、強制終了により `running` のまま
  残ったバッチを `aborted` にする
- 入り口は CLI の `photolab doctor [--fix]` と GUI の［ツール］→［カタログを点検...］

設定ファイルは `%LOCALAPPDATA%\Photolab\config.toml` に置く
（Linux 移管時は `~/.local/share/photolab/` / `~/.config/photolab/`）。
