## 1. 背景と目的

現状、カードを挿しても Photolab は何もしない。ショートカットから手動で起動し、
起動時に検出された媒体を選ぶ流れになっている。

**カードを挿したら勝手に立ち上がる**ようにして、取り込み忘れと手間を減らす。

architecture.md §5.1 で方式は決めてある。

> 自動起動は Windows の AutoPlay ではなく**常駐プロセスによるポーリング**で実装する
> （AutoPlay は Linux 移管時に捨てることになるため）。

### 完了条件

1. ログイン後、常駐プロセスが自動で動いている
2. カードを挿すと Photolab が立ち上がり、そのカードが選択された状態になる
3. 常駐を止める/再開する手段がユーザーにある
4. 二重に立ち上がらない（常駐も本体も）

## 2. スコープと設計判断

### 2.1 変更すること

```
photolab/
  core/
    watcher.py       媒体の出現/消失を検出する（GUI 非依存・ポーリング）
  ui/
    tray.py          タスクトレイ常駐。検出したら本体を開く
  cli.py             `photolab watch` サブコマンドを追加
tools/
  make_shortcut.ps1  スタートアップ登録の対応を追加（-Startup）
```

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 | 理由 |
| :--- | :--- | :--- |
| Windows の AutoPlay 連携 | **やらない** | architecture.md §5.1。Linux 移管時に捨てる資産になる |
| 常駐プロセスが取り込みを行う | **やらない** | 常駐は「検出して知らせる」だけ。**勝手にコピーしない**。取り込みは必ず人が確認してから |
| サービス / タスクスケジューラ登録 | **やらない** | 管理者権限が要る。スタートアップフォルダで足りる |
| カードの内容を常時スキャンする | **やらない** | 検出は `DCIM/` の有無だけ。走査は本体を開いてから |

## 3. 変更内容

### 3.1 `core/watcher.py`

`scanner.find_media()` を定期的に呼び、**前回との差分**を出すだけの薄い層。

- `MediaWatcher.poll()` が「新しく現れた媒体」を返す
- 挿しっぱなしのカードで繰り返し発火しない（前回の集合を覚えておく）
- 抜いたら忘れる（同じカードを挿し直せば再び発火する）
- GUI 非依存。タイマーは呼び出し側（`ui/tray.py`）が持つ

### 3.2 `ui/tray.py`

`QSystemTrayIcon` で常駐する。

- 一定間隔で `MediaWatcher.poll()` を呼ぶ
- 新しい媒体を検出したら本体ウィンドウを開く（または前面に出す）
- メニュー: 「Photolab を開く」「自動検出を止める/再開する」「終了」
- 本体を閉じてもトレイには残る（常駐なので）

### 3.3 多重起動の防止

- **常駐**: 二重起動すると同じカードで2回開いてしまう
- **本体**: 検出のたびに新しいウィンドウが増えると邪魔

いずれも1つに保つ。方式は §4-Q4 で確定させる。

### 3.4 スタートアップ登録

`tools/make_shortcut.ps1` に `-Startup` を追加し、
`shell:startup` に `photolab watch` のショートカットを置く。
**管理者権限は不要**で、フォルダからショートカットを消せば解除できる。

## 4. ユーザー確認事項

**着手前にここを合意する。** 括弧内はエージェントの推奨案。

### Q1. 常駐の形態

- (a) **タスクトレイ常駐アプリ**（`photolab watch`）が検出し、本体を開く
- (b) 本体 GUI を常に起動しておき、閉じたらトレイに最小化する

**推奨: (a)。** 決め手はメモリではなく**可視性と制御**。
「カードを挿すと勝手にウィンドウが開く」挙動は、動いているかが見えて、
いつでも止められないと不信感につながる。

**実測（2026-08-12 / `photolab watch` 常駐時）**:
ワーキングセット **67 MB** / コミット **265 MB**。

> 最初の計測は 0.9 MB という不自然な値になった。原因は
> **venv の `python.exe` がリダイレクタ**で、実体は別プロセスだったこと。
> スタブ側を測っていた。ロックファイルに書かれた PID（＝実体）を測って解決した。
> 常時 67 MB は、写真取り込みという用途では許容範囲と判断する。

**検討した他の選択肢**:

| 方式 | 常駐 | 反応 | 可視性・制御 |
| :--- | :--- | :--- | :--- |
| (a) タスクトレイ常駐 | あり | 2秒以内 | アイコンで見え、メニューで止められる |
| (b) トレイ無しの軽量常駐 | あり（軽い） | 2秒以内 | 動作が見えず、止めるにはタスクマネージャ |
| (c) OS のデバイス到着イベント | あり | 即時 | (a) と同じ |
| (d) タスクスケジューラのイベントトリガ | **なし** | 数秒 | 登録/解除が分かりにくく、USB 全般で発火 |

**決定: (a)。**

### Q1-2. イベント駆動にしないのか（将来の選択肢として記録）

**共通の API が無い**のが理由。Qt もデバイス到着の通知を提供していない
（`QStorageInfo` に変更通知は無く、`QFileSystemWatcher` は Linux の
マウント先には使えても Windows のドライブレター出現は監視できない）。

| OS | API | 備考 |
| :--- | :--- | :--- |
| Windows | `WM_DEVICECHANGE` | 隠しウィンドウでメッセージを受ける |
| Linux | udev モニタ（`pyudev`） | カーネルの uevent を netlink で受ける |
| Linux | udisks2 の D-Bus シグナル | **マウント先のパスが直接取れる**ので用途に合う |
| Linux | inotify で `/media/$USER` を監視 | `QFileSystemWatcher` で追加依存なしに書ける |

イベント駆動にすると**OS ごとに別実装を2本抱える**ことになる。
一方でポーリングは1本でどこでも動き、ドライブレターの列挙だけなので軽い。
カードを挿してから2秒は体感でほぼ問題にならない（挿す動作自体に1秒はかかる）。

**決定: まずポーリングで作る。** `MediaWatcher` は「前回との差分を返す」だけの層なので、
**中身を差し替えても呼び出し側は変わらない**。実際に遅いと感じたとき、
あるいは Linux へ移すときに、必要な側だけ実装する。

### Q2. 検出したときの動作

- (a) **すぐ本体ウィンドウを開く**
- (b) 通知（トースト）だけ出し、クリックしたら開く
- (c) 設定で選べるようにする

**推奨: (c) で既定は (a)。** 「自動起動」が目的なので既定は開く。
ただし作業中に勝手に前面へ出るのが煩わしい場面は必ずあるので、
設定で (b) に落とせるようにする。

**決定: 推奨のとおり。**

### Q3. ポーリング間隔

**推奨: 2 秒。** ドライブレターの列挙だけなので負荷はごく小さい。
カードを挿してから反応するまでの体感を優先する。

> 実測して重ければ延ばす。`find_media()` は A〜Z のドライブを見て
> `DCIM` の有無を調べるだけで、カードの中身は読まない。

### Q4. 多重起動の防止方式

- (a) **名前付きミューテックス**（Windows）/ ロックファイル（Linux）
- (b) ロックファイルのみ（両対応・実装が単純）

**推奨: (b)。** `%LOCALAPPDATA%\Photolab\watch.lock` に PID を書き、
起動時に「そのPIDが生きているか」を確認する。Linux 移管時もそのまま使える。

**本体の二重起動**については、常駐から開く場合は**常駐が本体プロセスを覚えておき、
生きていれば前面に出すだけ**にする（新規起動しない）。

### Q5. 同じカードを挿しっぱなしにしたとき

**推奨: 発火は1回だけ。** 抜くまで再通知しない。
抜いて挿し直したら再び発火する。

取り込み後もカードは挿さったままなので、これがないと閉じるたびに開き直してしまう。

### Q6. 常駐を止める手段

**推奨: トレイメニューに「自動検出を止める」を置く**（常駐は残す）。
完全に止めるのは「終了」。スタートアップから外すのはショートカットの削除。

**決定: チェック式のトグル**（`[✓] 自動検出`）にする。
**止めた状態は設定に保存**し、再起動しても止まったままにする
（勝手に再開すると驚くため）。

### Q7. 検出対象を絞るか

現状 `find_media()` は「リムーバブル + `DCIM` あり」で判定する。
USB メモリに `DCIM` があれば反応してしまう。

**推奨: 絞らない。** 誤検出しても本体が開くだけで実害がない。
ボリュームラベルで絞ると Z6/Z50 以外のカードが使えなくなる。

**決定: 発火条件は「リムーバブル かつ `DCIM/` がある」。**
これは `scanner.find_media()` が既に行っている判定そのものなので、
新しい条件を足す必要はない。

- **`DCIM/` の有無しか見ない**（中身は読まない）。ポーリングを軽く保つため。
  空のカードでも開くが、本体が「取り込めるファイルがありません」を出すので実害はない
- ドライブが現れた直後はファイルシステムがまだ見えず、`DCIM/` の確認が
  失敗しうる。**例外は握って次のポーリングに回す**（`find_media()` は
  `OSError` を握る作りになっている）

## 7. 途中発生した課題

### 2026-08-12 / 空のカードスロットを叩いてプロセスが終了不能になった

配布版の `Photolab.exe` が**終了できない状態**になった。
タスクマネージャーからも「アクセスが拒否されました」。

**調査結果**:

```
所有者    : 現ユーザーと同じ（昇格していない）
スレッド数: 1
待機状態  : 5 / 待機理由 0（Executive = カーネル内で待機）
ドライブ  : G, H, I, K, L が type=2（リムーバブル）
```

**原因**: カードリーダーが**空のスロットにもドライブレターを割り当てる**。
`find_media()` は A〜Z 全部に `is_dir()` を掛けていたので、
メディアの無いドライブを叩いていた。Windows はこのとき
「ドライブにディスクを挿入してください」というシステムモーダルを出し、
プロセスはカーネル内で待機したまま終了もできなくなる。

**対応**:

- **ドライブ種別を先に見る。** `GetDriveTypeW` はデバイスに触らずに答えるので、
  リムーバブル以外はここで除ける（固定ディスクや光学ドライブを叩かない）
- 残りは `_quiet_device_errors`（`SetThreadErrorMode` +
  `SEM_FAILCRITICALERRORS`）の中で調べ、**ダイアログを出させない**。
  プロセス全体の `SetErrorMode` にしないのは他スレッドへの影響を避けるため
- `has_dcim()` の `OSError` を握って次のドライブへ進む

**実測**: 修正後 `find_media()` は **13 ms**（リムーバブル5台ある環境）。

**追加対応（同日）**: ダイアログを抑えても I/O 自体が遅ければ待たされるため、
**検出をワーカースレッドへ移した**（`ui/workers.py` の `WatchWorker`）。

- **タイマーはワーカースレッドの中で作る。** GUI スレッドで作ったタイマーを
  `moveToThread` しても、発火は元のスレッドのままになる
- 自動検出のオン/オフは**シグナル経由で依頼する**（別スレッドのタイマーを
  GUI スレッドから直接触らない）
- 検出結果は `detected` シグナルでキューイングされ、GUI スレッドで受ける

**確認**: `find_media()` の差し替え先で呼び出しスレッド名を記録したところ、
`Dummy-1`（ワーカー）で動いており `MainThread` では呼ばれていない。
